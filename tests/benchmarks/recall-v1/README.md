## What this is

The locked evaluation set for `engram recall`'s progressive-disclosure navigator
(ADR-0005). It fixes both halves of an evaluator:

- `vault/` — a **static, OKF-valid** knowledge vault of **126 concepts** across
  **20 nested directory indexes**, with realistic descriptions, tags, and
  cross-links. Every `index.md` was generated by the real `reindex` (ADR-0006
  format), so the navigator descends the exact production format.
- `eval.json` — the **query set** and the **scalar**: for each query the
  `expectedConceptIds` (recall-correctness) plus `maxBodyReads` and
  `maxFilesFraction` bounds (the bounded-read budget, M3/M6).

## The scalar (what "better" means)

1. **recall@K = 100%** — every `expectedConceptIds` entry appears in the returned
   minimal set (`tests/retrieval/recall-bounded.test.ts`).
2. **Bounded body reads (M6)** — `ReadReport.bodyReads <= maxBodyReads` and
   `bodyReads < conceptCount`: never a whole-vault body load.
3. **Bounded file fraction (M3)** — `filesTouched / conceptCount <=
   maxFilesFraction`: navigation touches a small, sublinear fraction of files
   (~16% here: it reads the ~20 index maps, not the 126 bodies).

## Metric definition (ADR-0010)

Only **body-tier** reads (full concept content — the context-consuming
operation) are what M3/M6 constrain. `index` / `frontmatter` / `grep` reads
return one-line-per-concept metadata and never surface a body, so scanning the
index map is bounded auxiliary I/O, not a "whole-vault read".
